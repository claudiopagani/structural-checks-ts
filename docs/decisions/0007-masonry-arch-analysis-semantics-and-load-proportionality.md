# Decision 0007 — Masonry-arch analysis semantics and load proportionality

## Context

The masonry-arch module already had two mechanically distinct formulations: direct rigid-block
equilibrium/limit analysis and incremental equilibrium with deformable interfaces. The incremental
solver also exposed load, displacement, and spherical arc-length control. The API did not separately
name the engineering objective, however, and callers could incorrectly infer that the continuation
control defined whether an operation was a design check, capacity calculation, or advanced path.

The nonlinear result also used `lambdaCritical` for both a physical material limit and exhaustion of
the minimum numerical step. That made a solver failure look like an engineering capacity. Static
results exposed fixed and scalable load cases, but nonlinear results did not carry the same complete
load-pattern metadata.

## Decision

Every analysis distinguishes three independent levels:

1. the mechanical model, including rigid-plastic or deformable interface response and reference or
   finite rigid-block kinematics;
2. the engineering `analysisObjective`;
3. the numerical strategy, including continuation `control` where applicable.

The public objectives are:

```ts
type MasonryArchAnalysisObjective = "design-state-check" | "capacity" | "advanced-path";
```

The continuation controls remain:

```ts
type MasonryArchContinuationControlType = "load" | "displacement" | "arc-length";
```

No control value implies an objective. The current assigned-state API accepts only
`design-state-check`; the direct static-limit API accepts only `capacity`. Incremental deformable
analysis accepts all three objectives. A nonlinear `design-state-check` currently requires load
control to `targetLambda: 1`; this is an explicit supported combination, not an equivalence between
load control and design checking.

`design-state-check` and `capacity` retain first-material-limit termination. Setting
`stopAtFirstMaterialLimit: false` is accepted only for `advanced-path`, where the caller explicitly
requests continuation under the selected post-limit constitutive assumptions.

For compatibility, `analyzeMasonryArchState` defaults to `design-state-check`, direct
`analyzeMasonryArchCollapse` defaults to `capacity`, and direct `analyzeMasonryArchNonlinear`
defaults to `advanced-path`. The nonlinear compatibility route through `analyzeMasonryArchCollapse`
defaults to `capacity`.

## Definition of lambda

Combination factors are resolved first. The factored load cases are then partitioned for the
individual analysis:

```text
F(lambda) = F_fixed + lambda * F_scalable

F_fixed    = sum(gamma_j F_j,fixed)
F_scalable = sum(gamma_k F_k,scalable)
```

One scalar `lambda` may multiply any number of selected load cases. This directly represents, among
other patterns:

```text
G + lambda Q
lambda (G + Q)
G1 + lambda (G2 + Q1)
```

The fixed/scalable role is not part of a physical load or permanent model state. It belongs to one
analysis invocation. At `lambda = 1`, the complete base combination is present after its factors are
applied.

`lambda` is a load-pattern parameter and is not generally a safety factor. It scales external
load-case contributions only. It does not scale:

- initial tendon force `T0`;
- passive-tendon force generated by deformation compatibility;
- support reactions;
- contact and deviator actions;
- anchor demands, bonded-layer response, or other quantities solved from equilibrium and
  compatibility.

Every collapse and nonlinear result carries a typed `analysis.lambda` definition containing the
expression, fixed and scalable case identifiers, base and effective factors, current `lambda`, the
meaning of one, and excluded response quantities. Every converged nonlinear step also carries its
effective load-case factors, including the separate proportional fixed-load initialization stage.

## Termination and capacity

Numerical termination and engineering outcome remain separate. The existing
`convergenceInfo.termination` identifies the solver event. `analysisOutcome` identifies whether the
declared objective was satisfied, not satisfied, not reached, or not verifiable.

A nonlinear `lambdaCritical` is returned only for a `capacity` objective that reaches a physical
material limit. Minimum-step exhaustion, maximum steps, and fixed-preload convergence failure are
numerical failures and never define capacity. `limitState` may record a physical limit encountered
during another objective without relabelling that analysis as capacity.

## Consequences

- The same control algorithm may be used for different engineering objectives without changing its
  meaning implicitly.
- Capacity comparisons require equal objectives in addition to equal geometry, loading, combination
  factors, and fixed/scalable roles.
- Existing result fields remain available. New typed descriptors and outcomes are additive, except
  that a numerical minimum-step termination no longer populates nonlinear `lambdaCritical`.
- Mechanical model validation fails before continuation when any required interface lacks explicit
  deformability.
- The decision changes no masonry formula, interface law, tendon constitutive relation, or normative
  conformity status.
